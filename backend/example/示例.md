# 量化交易系统后端示例

## 后端各层调用方式

### 分层结构

```
┌─────────────────────────────────────────────┐
│              Frontend（前端）                │
├─────────────────────┬───────────────────────┤
│   执行层 (Execution) │   风控层 (RiskControl) │
│   OrderExecutor     │   RiskController      │
│                     │   RiskEventServiceImpl│
├─────────┬───────────┴──────┬────────────────┤
│         │  common / interfaces               │
│         │  RiskEventHandler（抽象接口）        │
│         │  common / models                   │
│         │  RiskEvent（数据模型）               │
└─────────┴────────────────────────────────────┘
```

### 数据流向一：执行层 → 推送 → 风控层（依赖注入）

执行层在关键节点主动将数据推送给风控层，采用的是**依赖注入**模式：

```
执行层（OrderExecutor）         风控层（RiskEventServiceImpl）
        │                              │
        │ ① 持有 RiskEventHandler 引用   │
        │    （构造函数注入）              │
        │                              │
        │ ② 发生事件时调用               │
        │ ────── handleRiskEvent() ───→ │
        │                              │
```

- **接口定义方**：`common/interfaces/risk_interface.py` 定义了 `RiskEventHandler` 抽象类
- **实现方**：`risk_control/services/risk_service.py` 实现了该接口
- **注入方**：`main.py` 在组装阶段将实现注入到执行层
- **调用方**：`execution/services/order_executor.py` 通过接口调用风控处理

这样执行层不依赖风控层的具体实现，只依赖抽象接口。

### 数据流向二：风控层 → 拉取 → 执行层（查询接口）

当风控层需要主动获取数据时，方向反转：

```
执行层（OrderExecutor）         风控层（RiskController）
        │                              │
        │ ① 定义查询接口（如 OrderQuery） │
        │    （接口在 common 层定义）      │
        │                              │
        │ ② 风控层需要数据时主动调用      │
        │ ←─── getOrderInfo() / ─────── │
        │      getCurrentPosition()     │
        │                              │
```

- 执行层定义查询接口，风控层持有该接口的引用
- 风控层在需要决策时主动拉取上下文数据
- 实质是控制权反转（IoC），谁需要数据谁定义接口

### 依赖注入组装（main.py）

```python
# 1. 实例化风控服务（接口的实现）
risk_handler: RiskEventHandler = RiskEventServiceImpl()

# 2. 通过构造函数注入到执行层
order_executor = OrderExecutor(risk_handler=risk_handler)
```

所有依赖关系在 `main.py` 中一次性组装完成，各模块之间只依赖抽象接口。

### 总结：后端各层调用模式

后端业务层之间的调用，本质上就是**谁需要数据、谁依赖接口**，归结为以下两种模式：

| 模式 | 数据流向 | 接口定义方 | 接口实现方 | 引用持有方 | 适用场景 |
|------|---------|-----------|-----------|-----------|---------|
| **依赖注入（推送）** | 调用方 → 实现方 | 接收数据的一方 | 接收数据的一方 | 推送数据的一方 | 执行层主动上报事件、日志、指标给风控或监控层 |
| **查询接口（拉取）** | 实现方 → 调用方 | 提供数据的一方 | 提供数据的一方 | 需要数据的一方 | 风控层按需查询订单状态、持仓信息等 |

**通用规则：**

1. **上层依赖下层，下层不依赖上层** — 执行层可以引用 `common` 层的接口和模型，但 `common` 层不引用任何业务层的实现
2. **面向接口编程** — 业务层之间不直接引用具体类，只通过 `common/interfaces` 中的抽象接口交互
3. **组装与业务分离** — 所有依赖的实例化与注入集中在 `main.py`（或独立的 DI 容器），业务代码只声明「我需要什么接口」
4. **如果需要双向调用**，则定义两组接口，放在 `common/interfaces` 中，双方各持对方的接口引用：

```
  OrderExecutor                   RiskController
      │                                │
      │──→ handleRiskEvent() ──────→   │   推送（执行层持风控接口）
      │                                │
      │←── getOrderInfo() / ────────   │   拉取（风控层持执行层接口）
      │     getPosition()              │
```

## 后端与前端交互方式（FastAPI）

### 交互模型

```
浏览器 / 客户端                FastAPI 服务
     │                             │
     │────── HTTP 请求 ──────────→ │  ← 路由匹配
     │                             │  ← 参数校验（Pydantic）
     │                             │  ← 业务处理
     │←─── JSON 响应 ──────────── │  → 自动序列化
```

后端通过 **FastAPI** 暴露 RESTful API，前端通过 HTTP 调用。

### 已定义的 API 端点

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/risk/events` | 查询风控事件列表 |
| GET | `/api/v1/risk/events/summary` | 获取风控事件汇总 |

端点定义在 `risk_control/api/risk_controller.py`，通过路由注册到 `main.py`：

```python
app.include_router(risk_router)
```

### 通信细节

| 方面 | 说明 |
|------|------|
| 协议 | HTTP/1.1（FastAPI 默认，可升级为 HTTP/2） |
| 请求体 | JSON，通过 Pydantic 模型自动校验 |
| 响应体 | JSON，通过 `response_model` 自动序列化 |
| 参数来源 | 路径参数、查询参数（Query）、请求体 |
| 文档 | FastAPI 自动生成 Swagger UI：`/docs` |
