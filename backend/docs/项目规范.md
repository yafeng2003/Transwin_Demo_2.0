# 项目规范

---

## 一、项目文件结构

```
量化交易系统后端/
│
├── common/                       # 公共层（接口定义、数据模型、配置工具）
│   ├── interfaces/               # 层间通信接口定义
│   ├── models/                   # 数据模型（Operation/Deal/Asset/Trade等）
│   ├── config/                   # 配置管理
│   └── utils/                    # 工具函数（日志、数据库连接等）
├── strategy/                     # 策略层 —— 信号生成与策略调度
│   └── tests/                    # 策略层单元测试
├── execution/                    # 执行层 —— 下单/撤单/成交同步/算法单
│   └── tests/                    # 执行层单元测试
├── risk_control/                 # 风控层 —— 风险监控与熔断
│   └── tests/                    # 风控层单元测试
├── notification/                 # 通知系统 —— 邮件等消息通知
│   └── tests/                    # 通知系统单元测试
├── data_analysis/                # 数据分析层 —— 分析计算与报表
│   └── tests/                    # 数据分析层单元测试
├── infrastructure/               # 基础服务 —— 数据库/日志/定时任务
│   └── tests/                    # 基础服务单元测试
│
├── docs/                         # 项目文档
│   ├── 前端功能需求文档.md
│   ├── 后端功能需求文档.md
│   ├── 数据库设计.md
│   ├── 后端内部接口.md
│   ├── 项目规范.md
│   ├── Git协作流程.md
│   └── 分工文档.md
│
└── README.md
```

### 结构说明

| 目录 | 说明 |
|------|------|
| `common/` | 公共层，所有模块共享。`interfaces/` 放层间接口定义，`models/` 放数据模型，`config/` 放配置，`utils/` 放工具函数 |
| `common/interfaces/` | **所有跨层调用必须通过此目录的接口进行** |
| `common/models/` | Operation、Deal、Asset、Trade、ActivePosition、RiskEvent 等数据模型 |
| `strategy/` | 策略层，负责信号生成与策略调度 |
| `execution/` | 执行层，负责交易所对接与订单执行 |
| `risk_control/` | 风控层，负责风险监控与熔断 |
| `notification/` | 通知系统，负责邮件等消息通知 |
| `data_analysis/` | 数据分析层，负责分析计算和报表生成 |
| `infrastructure/` | 基础服务，数据库操作、日志、定时任务 |
| `docs/` | 项目文档 |

## 二、测试目录结构

每个模块的单元测试放在对应模块下的 `tests/` 目录中，与代码同层：

```
strategy/
└── tests/               # 策略层单元测试
execution/
└── tests/               # 执行层单元测试
risk_control/
└── tests/               # 风控层单元测试
notification/
└── tests/               # 通知系统单元测试
data_analysis/
└── tests/               # 数据分析层单元测试
infrastructure/
└── tests/               # 基础服务单元测试
```

**测试要求**：
- 每个函数和方法都要有对应的测试用例，覆盖正常流程和异常情况。
- 所有外部依赖（数据库、交易所 API、第三方服务）必须 Mock，不能在单元测试中连接真实服务；测试时可以传入 Mock 对象替换真实实现。
- 测试数据量较大时，可在 `tests/` 下创建 `mock_data/` 目录存放 mock fixture。
- 提交代码前必须自测通过。

## 三、层间依赖规则

```
┌──────────────────────────────┐
│         策略层 strategy       │
├──────────────────────────────┤
│         执行层 execution      │
├──────────────────────────────┤
│  风控层 risk_control + 通知  │
├──────────────────────────────┤
│     数据分析层 data_analysis  │
├──────────────────────────────┤
│      基础服务 infrastructure  │
└──────────────────────────────┘
         ↕ 只能通过 interfaces 通信
    ┌──────────────────────┐
    │  common/interfaces   │
    │  common/models       │
    └──────────────────────┘
```

- 各层**只能依赖** `common/interfaces/` 和 `common/models/`
- **禁止直接 import** 其他层的实现类
- **所有跨层调用**必须通过 `common/interfaces/` 中定义的接口进行

## 四、代码风格

| 规范 | 要求 |
|------|------|
| Python 版本 | 3.12 |
| 类型标注 | 所有函数参数和返回值必须标注类型 |
| 依赖注入 | 构造函数通过参数接收外部依赖，不在内部直接创建实例 |
| 接口通信 | 业务代码依赖接口而非具体实现 |
| 数据传递 | 使用定义好的数据模型，禁止字典或全局变量传递结构化数据 |
| 代码风格 | 代码拼写和格式保持规范，注释不使用表情符号 |
| 注释原则 | 注释只写"为什么"，不写"是什么"（详见下节） |

---

## 五、注释规范

注释只写"为什么"，不写"是什么"。代码本身应该通过清晰的命名说明自己在做什么。

**需要写注释的情况：**
- 使用了不常见的实现方式，说明为什么选择这个方案。
- 业务逻辑中存在边界条件或特殊处理，说明触发条件和处理依据。
- 接口函数说明参数含义和异常情况。

**不需要写注释的情况：**
- 代码本身已经表达了意图。
- 逐行解释运算过程。
- 空泛的说明。
